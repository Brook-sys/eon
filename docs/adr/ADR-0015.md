# ADR-0015: Catálogo multi-provedor / multi-modelo com discovery e seleção por capacidade

- **Status**: aceito (2026-10-13)
- **Origem**: pedido explícito do operador (2026-10-13); estende D05, D10, D27, D29 — docs/plan/00-DECISIONS.md

## Contexto

O contrato único OpenAI-compat (D05) já aceita qualquer provedor que fale `/v1/chat/completions` — mas o desenho corria o risco de assumir **um binding configurado** e **modelos escolhidos por nome**. A realidade do operador é plural: Groq como um provedor, o 9router local como outro (servindo modelos com nomes personalizados como `topmodel`), Ollama eventualmente. E modelos **vêm e vão** — qualquer nome citado hoje pode não existir amanhã. Nome de modelo é string opaca; capacidade se **mede**, nunca se assume por marca.

## Decisão

1. **Pluralidade é o default**: o sistema opera com N bindings simultâneos. Binding = (nome, base_url, key, perfil de dialeto). Ex.: Groq + 9router local + Ollama ao mesmo tempo.
2. **Discovery obrigatório no boot**: `GET /v1/models` por binding → catálogo de candidatos (binding, modelo). **Nenhum nome de modelo hardcoded** em código, config default ou docs contratuais — só em config explícita do operador.
3. **Seleção por capacidade medida**: as probes determinísticas de calibração (D27) aplicadas a cada candidato que o scheduler quiser usar; nível por MÍNIMO (fail-safe); seleção = nível × custo × limites. Modelos de endpoint personalizado (`topmodel` via router) são candidatos de primeira classe.
4. **Churn como classe de evento**: modelo sumiu (404/model_not_found) → classe de erro D29 → drop do catálogo + re-discovery + próximo candidato. O autômato nunca para nem espera humano por causa de churn (invariante 1).
5. **Cache de calibração por (binding, modelo, versão-perfil)**: o mesmo modelo via router ≠ via provedor direto — latência e confiabilidade diferem; o cache reflete isso.
6. **Serialidade preservada (D10)**: catálogo é ALCANCE, nunca paralelismo de cognição. Uma chamada de modelo em voo, sempre; discovery/calibração também respeitam o orçamento (calibração preguiçosa: só candidato candidato a uso).
7. **Telemetria de uso per (binding, modelo)**: latência, parse failures, cota consumida → alimenta scheduler e Lessons.

**Config**: `EON_MODEL_KEY` existente permanece como o binding **default** (retrocompatível com o que o operador já configurou); bindings nomeados por convenção de env do stack Portainer (forma exata decidida na implementação do M2, mascarada pela UI — D49; segredo nunca em prompt/flag/commit/sandbox).

## Consequências

- Contratos de M1 não podem assumir binding único (nada de "o modelo" no kernel; sempre "um candidato do catálogo").
- Implementação nasce no M2 (ordem D46 intacta: adapter → calibração → missão F1); M1 segue com provider fake determinístico.
- A avaliação de capacidades é agnóstica a marca por construção — o que a tese exige (modelos 7B a strong-tier, medidos igualmente).
- Custo de discovery: 1 chamada por binding no boot (barata); calibração preguiçosa limita o multiplicador N×M.
