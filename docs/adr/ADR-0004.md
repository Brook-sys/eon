# ADR-0004: Três camadas de processos L1/L2/L3; binários bons com SHA-256

- **Status**: aceito (2026-10-13)
- **Origem**: D06, D07, D41 — docs/plan/00-DECISIONS.md

## Contexto

"Nunca para" × "muda o próprio código" é a tensão central. Goroutine não se mata em Go; um build travado ou OOM dentro do core mataria o loop. A camada que protege não pode ser protegida por aquilo que ela protege.

## Decisão

L1 SUPERVISOR: imutável (muda só via imagem GHCR, via humano), stdlib-only, watchdog — spawn/backoff/restart do core; crash-loop → re-promove o último binário bom. L2 CORE: reiniciável, todo estado canônico em SQLite. L3 WORKERS: efêmeros, 1 job = 1 processo via stdio, sandbox cego. Sem sandbox, degrada para 2 camadas fail-closed (missão viva, F3-de-código pendente). Artefatos promovidos em `<data>/artifacts/eon/vN` (últimos 3 bons, D41): SHA-256 gravado no evento de promoção e RE-VERIFICADO pelo supervisor antes do swap; crash-loop da vN → demote para vN-1 → casca → mantém vivo no teto de backoff. NUNCA para por conta própria.

## Consequências

- Falha de build/teste/promoção nunca derruba o sistema; derruba a tentativa.
- O supervisor conhece o core como PROCESSO (sinais), nunca como import.
- M0 implementou: detecção de crash-loop com janela deslizante, verificação de SHA corrompido (rejeita), demote e health.json (ADR-0014 usa).
